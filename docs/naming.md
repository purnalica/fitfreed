# FitFreed Product Identity

## Status

The product name **FitFreed** was approved on 2026-08-15. It is the canonical identity for repository creation and implementation unless the project owner explicitly reopens the decision.

Preliminary collision screening reflects the same date. It is not formal trademark clearance.

## Canonical forms

- **Product name:** `FitFreed`
- **Repository slug and lowercase technical identifier:** `fitfreed`
- **Working descriptor:** *An open-source fitness data explorer.*
- **Working tagline:** *Your fitness data, freed.*

The internal capital `F` preserves the intended construction, *Fit + Freed*. Prose, interface copy, documentation, release artifacts, and visual identity use `FitFreed`. Repository names, package prefixes, and lowercase-only contexts use `fitfreed`.

## Meaning and positioning

The name combines the recognizable fitness cue *fit* with *freed*, the intended outcome for personal data that remains useful beyond its source platform. It is short, provider-neutral, and connected to the project's practical-freedom thesis without presenting the application as a legal service.

Public identity and copy must:

- Make clear that FitFreed explores personal fitness data rather than providing workouts, coaching, or medical diagnosis.
- Remain neutral across Polar Flow, Garmin, and future data providers.
- Avoid implying affiliation with a provider, regulator, or standards body.
- Use the descriptor wherever the standalone name would not communicate the product category.
- Keep the product globally understandable while the GDPR and EU Data Act remain part of its origin story.

## Known risks

- The name alone does not explicitly identify data exploration.
- Search engines may split the name into the Honda model names *Fit* and *Freed*.
- The health-software use of the standalone name *Freed* is close enough to require a formal confusion and trademark screen before public branding.
- The working descriptor and tagline have not undergone a dedicated brand, localization, or trademark review.

## Visual identity status

The AI-assisted draft asset set under the ignored local `docs/reports/art/` directory was reviewed on 2026-08-15 and is not approved for publication or relocation into repository assets.

The geometry is technically clean, scalable, and consistent with the data-freedom narrative. The SVG files are valid XML and contain no scripts, event handlers, external resources, embedded rasters, or runtime font dependencies. The supplied palette exceeds the applicable WCAG AA contrast thresholds, although the ratios stated in the draft guide are inaccurate.

The current concept combines a geometric `F`, detached pixel-like modules, and a purple accent. Preliminary design searches found this construction widely represented in stock lettermarks and adjacent application identities. That does not establish infringement, but it leaves distinctiveness and confusing similarity unresolved. The draft also requires confirmation of the AI generator terms, correction of non-English guidance, and consumer-specific asset generation before adoption.

No draft asset enters version control until the public-branding gate below is satisfied. Approval would then identify one canonical vector source, a reproducible derivative-generation process, explicit licensing and provenance, and the exact repository or application consumers for every retained file.

## Public-branding gate

Before public branding or release:

1. Repeat exact and confusingly similar name searches across GitHub, major package registries, application stores, and general web results.
2. Perform figurative and design-mark searches for the proposed visual identity, including stock-template and application-icon similarity.
3. Perform a preliminary trademark search in intended distribution regions and clearly distinguish it from legal clearance.
4. Verify the AI generator terms, declared source inputs, redistribution rights, and compatible licensing for every adopted asset.
5. Review the descriptor and tagline for clarity, localization, accessibility, and conflict risk.
6. Check relevant domain names and social handles if the project intends to use them.
7. Verify consistent `FitFreed` branding and lowercase `fitfreed` technical identifiers across public artifacts.
