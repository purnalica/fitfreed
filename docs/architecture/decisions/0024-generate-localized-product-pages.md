# ADR 0024: Generate localized product pages from one source

- **Status:** Accepted
- **Date:** 2026-08-18
- **Decision owners:** FitFreed maintainers and product owner
- **Related requirements:** [Product requirements](../../requirements.md)
- **Related delivery plan:** [MVP experience delivery](../../plans/mvp-experience-delivery.md)
- **Related architecture:** [Release delivery](../release-delivery.md), [ADR 0020](0020-compose-product-and-update-pages.md), [ADR 0023](0023-use-fitfreed-org-as-the-public-origin.md)

## Context

The product entrance at `https://fitfreed.org/` is currently an English static page. FitFreed supports
`en-US` and `es-ES`, and the public entrance must provide the same clear product proposition in both
languages without creating two independently maintained pages. A copied Spanish document would let
structure, claims, links, release status, accessibility, and metadata drift away from the English source.

The site must remain static, privacy-preserving, easy to contribute to, compatible with collaborative
translation tools, and composable with the byte-preserved `/updates/` subtree selected by ADR 0020.
Language negotiation must never make a localized URL unstable or prevent a user from choosing a
different language explicitly.

## Decision

FitFreed generates all localized product pages from one canonical English HTML source and versioned
locale catalogs.

- `site/index.html` is the only structural product-page source and contains the `en-US` source text.
- Translatable content has stable semantic keys. A separate `es-ES` JSON catalog contains Spanish
  values and is suitable for conventional translation tooling.
- Build-time validation rejects missing keys, extra keys, duplicate keys, or visible source content
  without an explicit translatable or language-neutral contract.
- The Pages artifact contains the English fallback at `/` and the Spanish page at `/es/`. Each route is
  a complete static document with its own language, title, description, canonical URL, and `hreflang`
  metadata.
- On the first visit to `/`, a minimal same-origin script chooses `es-ES` when the first supported
  browser preference is Spanish. Unsupported or unavailable preferences fall back to English.
- An explicit language choice is visible on every localized page, uses ordinary links without requiring
  JavaScript, and is persisted locally when storage is available. The persisted choice takes precedence
  on later visits to `/`.
- Direct visits to `/es/` remain Spanish. Automatic negotiation occurs only at the language-neutral root,
  so shared localized URLs are deterministic.
- The locale script performs no network request, creates no identifier, and fails safely when browser
  APIs or local storage are unavailable.
- `/updates/` remains language-neutral and is copied without byte changes. Localization is confined to
  product-page files.
- Local review serves the composed artifact rather than the source directory, ensuring localized routes
  are tested exactly as published.

## Consequences

- Product structure, accessibility, links, and release claims have one maintainable source.
- Translators work on a conventional catalog without editing HTML or generated pages.
- Page composition becomes a required localization boundary: source checks alone cannot represent the
  deployed Spanish route.
- A small script is accepted for preference negotiation and persistence; all page content and manual
  language navigation remain usable when it does not run.
- Adding a locale requires a complete catalog, route metadata, automated acceptance, and contributor
  documentation rather than a copied page.

## Verification

Acceptance requires:

1. Catalog validation proves exact key parity with the English source and the generated status block.
2. Both generated pages pass semantic, link, product-claim, responsive, and automated accessibility
   checks in their declared language.
3. Tests cover stored preference precedence, ordered browser-language negotiation, English fallback,
   storage failure, explicit switching, and stable direct localized routes.
4. Every localized page declares canonical and alternate-language URLs, including `x-default`.
5. Pages composition and remote verification cover every generated byte while preserving any complete
   `/updates/` snapshot exactly.
