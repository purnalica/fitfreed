# Milestone 2 Execution Plan

## Status

Active as of 2026-08-16. Milestone 1 established the production-shaped application, architecture, persistence, localization, contributor workflow, packaged E2E path, and private macOS release-evidence boundary used by this plan.

## Objective

Deliver the agreed private macOS MVP alpha: a person can import a compatible real Polar Flow personal-data ZIP, understand complete coverage, explore provider-neutral daily activity, training, sleep, and recovery history, compare periods visually, repeat and extend imports safely, recover from actionable failures, and evaluate an integrity-verified private update path.

The MVP is complete only as one usable journey. A domain parser, database table, chart, or package is not independently sufficient evidence.

## Scope protection

This plan includes only the confirmed MVP in the [product requirements](../requirements.md). Route maps, full-resolution physiological or training sample exploration, providers other than Polar Flow, Linux and Windows packages, Apple signing and notarization, advanced application-level encryption, and a runtime importer marketplace remain excluded.

The private reference export is local acceptance input, never a fixture or publication input. Versioned evidence remains independently constructed and synthetic. No exact private path, filename token, value, count, timestamp sequence, identifier, route, package fingerprint, database, log, or screenshot may enter Git or GitHub Actions.

[ADR 0012](../architecture/decisions/0012-publish-two-dimensional-upgrade-support.md) keeps application releases and library schemas as separate dimensions inside one target-bound contract. The first 0.1.0 matrix contains no application predecessor and cannot derive one from development history or synthetic packages. It separately declares schemas 1 through 9. Repository checks bind the matrix to npm, Tauri, Cargo, the compiled schema, and the immutable migrations. A table-driven integration test constructs every declared schema, verifies SQLite integrity, interrupts every required migration, proves rollback to the source marker, retries, and reaches schema 9. Release manifest version 2 requires the exact matrix as `supported-upgrades.json` with a size and SHA-256 digest; integrity verification also rejects a digest-consistent matrix for another target. Adding a real application baseline makes the packaged update gate fail until it derives complete release-package evidence for every declared target and source schema.

The infrastructure verifier bounds the raw response and decoded payload, rejects unknown fields and keys, verifies Minisign before parsing the payload, validates HTTPS package expectations up to the signed 1 GiB limit, and requires complete equality with the outer Tauri mirrors. The HTTPS adapter rejects dynamic or credential-bearing endpoint configuration, disables redirects and TLS key logging, bounds connection, total request, declared length, and streamed bytes, and maps unavailable transport separately from untrusted oversize or malformed content. The native package adapter resolves only the authorization's key from that same active trust set, rejects a non-current target or noncanonical URL, configures a five-second connection and fifteen-minute total request without redirects or TLS key logging, prepares Tauri from the authorization without another metadata read, rechecks exact version, target, URL, and signature, invokes the bounded download and Tauri package-signature verifier, and compares exact size and SHA-256 afterward. Transport and integrity failures remain distinct. Verified bytes are not exposed to React. The installation command accepts only the candidate version and obtains trust, package identity, paths, and native authority inside the host. The pinned updater source retains Tauri's operating-system installers, and a machine-readable source allowlist, exact checksums, original licenses, dependency pin, dedicated tests, and repository check make the refinement reproducible and reject unreviewed drift or frontend capability.

[ADR 0010](../architecture/decisions/0010-run-update-recovery-from-the-preserved-application.md) assigns external recovery to the verified previous executable. The version 1 local recovery contract binds one source application/library pair to its authorized target and permits only the documented lifecycle transitions. Preparation requires the canonical installed bundle and library, a newer candidate, and a current-or-newer target schema. The macOS copier preserves bundle metadata, while deterministic tree hashing verifies identity, version, executable, files, permissions, and bundle-confined symbolic links. The SQLite online backup verifies the unmodified current source and a reopened read-only destination with exact schema and `PRAGMA integrity_check`; temporary files, private permissions, synchronization, and atomic promotion protect the previous backup. A closed manifest and no-clobber active pointer become visible only after the pair reopens and verifies. Restoration revalidates both assets and caller-independent canonical destination bindings before mutation, stages the previous bundle beside the installation, retains the failed candidate, removes only the inactive library's fixed WAL and shared-memory sidecars, and atomically promotes the previous library. Re-entry after application quarantine or complete restoration converges on the same pair and terminal `recovered` phase. Invalid manifests, tampering, escaping or boundary symlinks, interrupted preparation or restoration, a second active attempt, an old schema, and illegal transitions fail closed. The host now routes the exact private watchdog invocation before desktop startup, and the runner requires a bounded process-bound readiness record from the preserved executable. One runner holds the watchdog lease, observes locked lifecycle state, retains the original absolute installation and confirmation deadlines across restart, launches the exact replacement, and atomically records its operating-system process identity and fresh nonce before releasing its startup gate. A restarted runner accepts an inherited candidate only while macOS still reports the exact PID, start time, and executable path; it revalidates that identity before each signal, obtains recovery authority atomically, stops the candidate, acquires its released lease before mutation, retries verified restoration, and relaunches only after `recovered`. The candidate host accepts only the closed recovery-identifier and nonce arguments plus matching private pipe record, validates its exact process identity and installation, retains a process-lifetime lease outside React, and serializes a no-argument frontend readiness signal through the existing full confirmation validator.

The application coordinator now reserves one exclusive desktop operation across fresh authorization, package download, recovery preparation, and native installation; imports and updates reject overlap in either direction. The installer resolves the installed bundle and library internally, prepares and verifies the pair, waits for watchdog readiness, records `replacement-started`, invokes the verified Tauri package installer, records `replacement-installed`, and exits the original application. Native failure records `recovering` so the live watchdog restores the pair. A watchdog startup failure or a stopped watchdog before the first transition permits removal of only the still-quiescent `prepared` attempt under every recovery lock. React offers `Install and restart` only when application policy marks the authenticated candidate installable, sends only its exact version, disables update, import, archive-selection, and locale mutations, restores those controls after failure, and maps fixed privacy-safe failure codes in both locales. After exact terminal destination validation, maintenance writes a minimal outcome receipt before removing the matching active pointer, failed candidate where applicable, and verified attempt under every recovery process lock.
