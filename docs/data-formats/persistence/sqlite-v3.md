# SQLite Persistence Schema Version 3

## Status and boundary

Historical local-library schema superseded by later immutable migrations. Version 3 is the cumulative version 2 library plus the locale preference introduced by the immutable [`0003_locale_preference.sql`](../../../src-tauri/migrations/0003_locale_preference.sql) migration. The canonical fitness model and portable export remain separate contracts.

SQLite `PRAGMA user_version` stores value 3 after migration. New libraries apply [`0001_initial.sql`](../../../src-tauri/migrations/0001_initial.sql), [`0002_import_ledger.sql`](../../../src-tauri/migrations/0002_import_ledger.sql), and `0003_locale_preference.sql` in one transaction. Existing versions 1 and 2 apply only the later ordered assets they lack. Any migration error or injected interruption rolls back the DDL, data transformation, and version marker together.

The unchanged import-ledger, artifact-coverage, daily-activity, provenance, and conflict contracts remain normative in the [version 2 specification](sqlite-v2.md). Version 3 adds only the table below.

## `locale_preference`

The table has zero or one row. No row means that the user has not chosen or initialized a FitFreed locale yet; the presentation derives a supported locale from operating-system preferences and persists that explicit result before treating initialization as complete.

| Column | SQLite type | Null | Contract |
|---|---|---|---|
| `id` | INTEGER | no | Singleton primary key constrained to value 1. |
| `locale` | TEXT | no | Supported BCP 47 language tag constrained to `en-US` or `es-ES`. |
| `updated_at_utc` | TEXT | no | UTC update time generated by SQLite in ISO 8601 form. |

Updates use an upsert on `id` 1. The application boundary rejects any unsupported locale before persistence, and the database constraint independently prevents an invalid stored value. Locale selection does not rewrite imported information, import evidence, or canonical history.

## Compatibility behavior

- Versions 0, 1, and 2 migrate forward to version 3. Version 3 opens without migration. A later or otherwise unsupported version is rejected without modification.
- Version 2 to 3 migration adds an empty preference table and therefore preserves the effective first-run choice until the presentation initializes it from the operating system.
- Application updates retain the SQLite file, so a selected locale survives application and packaged-process restarts.
- Adding another supported locale requires an explicit schema migration as well as complete translation catalogs, application validation, UI selection, tests, and documentation. Silently accepting an arbitrary locale code is forbidden.

## Verification evidence

Adapter integration tests prove empty-state loading, `es-ES` persistence, update to `en-US`, reopen behavior, clean creation, and rollback and recovery of interrupted upgrades from versions 1 and 2. Application tests prove supported-locale parsing and use-case delegation. Component and packaged E2E tests prove first-run initialization, explicit selection, restart persistence, and localized date and number output.
